Security-check your AI-built app

The exact prompts I gave my AI agent to try to break into my own app. Paste them one at a time. They review and report; nothing gets changed.

The idea for these checks comes from Kem (@kem_glitch, Glitch Cat Club) and his reel on security when vibe coding. Credit to him; this page is how I turned it into prompts. Not sponsored.

This is not a professional audit. It catches common mistakes. If your app holds health records, legal records, payments at scale or someone's whole business, get a professional review as well.

What you need

  • An AI coding agent that can read your project: Claude Code, Codex or similar.
  • Your app on your own computer, ideally with a local or test copy of the database. The prompts tell the agent never to touch the live app.
  • Written for apps built on Supabase (React, Vite, Next.js…). Most checks apply to any backend; the agent will adapt them.

Tip: Claude Code also has /security-review. Type it in a session and Claude reads your code for common holes (injection, broken login or permission checks, unsafe data handling). Run it too: it reads the code, while the prompts below test your running app, including database settings that never appear in the code.

Supabase changed one default (Oct 30, 2026)

New tables are no longer opened to the app's API automatically; each one needs an explicit grant (changelog). Good, but existing tables keep the access they had, so an app built before then still needs the checks below. Supabase's Security Advisor (in the dashboard) is a useful first scan too.

0. Ground rules (paste first)

We're running a defensive security review of our own app. It's our product and we're hardening it. Rules for every check that follows:
- Read and test the LOCAL copy only. Never send a request to the live site or the production database, and never write to production data.
- Never print a secret's value. Name the variable and the file it lives in, nothing more.
- For each finding, mark it VERIFIED (you ran or read something that proves it) or ASSUMED (inferred), give file:line, and rate it BLOCKING / SHOULD-FIX / NOTE.
- Report findings; do not fix anything yet.
- Write the results to docs/security/review.md as you go.

Start by listing every database table, every database function, every server/edge function, and every place the frontend talks to the backend. That inventory is the map for the checks that follow.

1. Secrets and keys

Check 1, secrets. Find every key and credential the app uses. Answer:
1. Does any secret key (for Supabase: the service_role or secret key) appear anywhere that reaches the browser: a VITE_ or NEXT_PUBLIC_ variable, a built bundle, a committed file, or a client-side import? Only the public (anon / publishable) key may reach the frontend.
2. Is any secret committed to git, now or in history? Check with git log -p -S on each key's variable name, never by printing the value.
3. Do server functions read secrets from environment settings, not hard-coded values?
4. Is .env gitignored, and is there a .env.example holding names only?

2. Row-level security

Check 2, row-level security. For EVERY table the app's API can reach:
1. Is RLS enabled? List any table without it.
2. List each policy for select / insert / update / delete, and say in plain words who it lets do what.
3. Flag any policy that is "using (true)", that lets anonymous users write, or that lets one user read or change another user's rows.
4. Search the migrations and git history for any place RLS was disabled or a policy loosened "to make something work", and say whether it was ever reverted.
5. Prove the important ones on a LOCAL database with two test users: show that user A cannot read or change user B's records. Use the public key and a signed-in user's token, never the secret key.

3. Admin actions and server routes

Check 3, routes. Is the rule the code states the rule it enforces, and is the list of ways to reach privileged data complete?
1. List every server function and database function. For each, does it check the caller's identity AND role (admin / staff / user) on the server side? A check that exists only in the UI doesn't count.
2. Can a user reach another user's records by changing an id in a request? Test that case for the app's most important records.
3. Are "security definer" functions limited to what they need, with search_path set?
4. Does anything return more fields than the screen shows (emails, phone numbers, payment data)?

4. Login abuse and hosting

Check 4, login and hosting.
1. Login, sign-up, password reset and any code entry: what limits the number of attempts? Check the auth rate-limit settings and any custom endpoint. Say what stops a bot guessing forever.
2. Are the storage buckets private where they should be? List each bucket, whether it is public, and its policies.
3. Is the database reachable only through its API, with no open direct connection string anywhere public?
4. Do preview or staging deployments use separate keys and data, or do they point at production?

5. AI inputs (only if your app uses AI)

Check 5. Does any feature send user-written text, uploaded files or web content to an AI model? If so: is that content treated strictly as data, never as instructions? Can it make the AI call a tool, reveal a system prompt, or write to the database? If no AI is used anywhere, say so and skip this check.

6. Backups, then the summary

Check 6, production readiness. Are database backups on, and has a restore ever been tested? Where would we restore from, and how long would it take? Then summarise all six checks: BLOCKING findings first, each with VERIFIED or ASSUMED, file:line and a one-line fix idea. Do not fix anything.

After the review

Fix the BLOCKING findings first, one at a time, and re-run the check that found each one. Then add standing rules so the agent doesn't undo the work next week. Put them in your agent's instructions file (CLAUDE.md for Claude Code, AGENTS.md for Codex):

## Security rules
- Never disable row-level security or loosen a policy to fix an error. Stop and ask.
- Secret keys never reach the browser or a public (VITE_ / NEXT_PUBLIC_) variable.
- No server function without a server-side identity and role check.
- Login and code-entry endpoints are rate limited.
- Stop and ask before changing anything public: buckets, policies, auth settings.

Revisa la seguridad de tu app hecha con IA

Los prompts exactos que le di a mi agente de IA para intentar entrar a mi propia app. Pégalos uno por uno. Revisan e informan; no cambian nada.

La idea de estas revisiones viene de Kem (@kem_glitch, Glitch Cat Club) y su reel sobre seguridad al programar con IA. El crédito es suyo; esta página es cómo lo convertí en prompts. No patrocinado.

Esto no es una auditoría profesional. Detecta errores comunes. Si tu app guarda historias clínicas, datos legales, pagos a gran escala o el negocio entero de alguien, pide también una revisión profesional.

Qué necesitas

  • Un agente de IA que pueda leer tu proyecto: Claude Code, Codex o similar.
  • Tu app en tu propia computadora, idealmente con una copia local o de prueba de la base de datos. Los prompts le dicen al agente que nunca toque la app en vivo.
  • Pensado para apps hechas con Supabase (React, Vite, Next.js…). Casi todas las revisiones sirven para cualquier backend; el agente las adapta.

Consejo: Claude Code también tiene /security-review. Escríbelo en una sesión y Claude lee tu código buscando fallas comunes (inyección, controles de login o permisos rotos, manejo inseguro de datos). Úsalo también: lee el código, mientras que los prompts de abajo prueban tu app funcionando, incluida la configuración de la base de datos que nunca aparece en el código.

0. Reglas básicas (pégalo primero)

Vamos a hacer una revisión de seguridad defensiva de nuestra propia app. Es nuestro producto y lo estamos reforzando. Reglas para cada revisión que sigue:
- Lee y prueba SOLO la copia LOCAL. Nunca envíes una solicitud al sitio en vivo ni a la base de datos de producción, y nunca escribas en datos de producción.
- Nunca imprimas el valor de un secreto. Nombra la variable y el archivo donde está, nada más.
- Para cada hallazgo, márcalo VERIFICADO (ejecutaste o leíste algo que lo prueba) o SUPUESTO (deducido), da archivo:línea y califícalo BLOQUEANTE / CORREGIR / NOTA.
- Informa los hallazgos; no corrijas nada todavía.
- Escribe los resultados en docs/security/review.md a medida que avanzas.

Empieza listando cada tabla de la base de datos, cada función de la base de datos, cada función de servidor/edge y cada lugar donde el frontend habla con el backend. Ese inventario es el mapa para las revisiones que siguen.

1. Secretos y claves

Revisión 1, secretos. Encuentra cada clave y credencial que usa la app. Responde:
1. ¿Aparece alguna clave secreta (en Supabase: la service_role o la secret key) en algún lugar que llegue al navegador: una variable VITE_ o NEXT_PUBLIC_, un bundle compilado, un archivo en git o un import del lado del cliente? Solo la clave pública (anon / publishable) puede llegar al frontend.
2. ¿Hay algún secreto en git, ahora o en el historial? Revísalo con git log -p -S sobre el nombre de la variable de cada clave, nunca imprimiendo el valor.
3. ¿Las funciones de servidor leen los secretos de la configuración del entorno, no de valores escritos en el código?
4. ¿El .env está en .gitignore, y hay un .env.example que solo tiene los nombres?

2. Seguridad a nivel de fila (RLS)

Revisión 2, seguridad a nivel de fila. Para CADA tabla que la API de la app puede alcanzar:
1. ¿Tiene RLS activado? Lista las que no.
2. Lista cada política de select / insert / update / delete y explica en palabras simples a quién deja hacer qué.
3. Señala cualquier política que sea "using (true)", que deje escribir a usuarios anónimos, o que deje a un usuario leer o cambiar las filas de otro.
4. Busca en las migraciones y en el historial de git cualquier lugar donde se desactivó RLS o se aflojó una política "para que algo funcione", y di si se revirtió.
5. Prueba las importantes en una base de datos LOCAL con dos usuarios de prueba: demuestra que el usuario A no puede leer ni cambiar los registros del usuario B. Usa la clave pública y el token de un usuario con sesión iniciada, nunca la clave secreta.

3. Acciones de admin y rutas del servidor

Revisión 3, rutas. ¿La regla que dice el código es la regla que aplica, y está completa la lista de caminos para llegar a datos privilegiados?
1. Lista cada función de servidor y de base de datos. Para cada una, ¿verifica la identidad Y el rol de quien llama (admin / staff / usuario) del lado del servidor? Una verificación que solo existe en la interfaz no cuenta.
2. ¿Puede un usuario llegar a los registros de otro cambiando un id en una solicitud? Prueba ese caso con los registros más importantes de la app.
3. ¿Las funciones "security definer" están limitadas a lo que necesitan, con search_path definido?
4. ¿Algo devuelve más campos de los que muestra la pantalla (correos, teléfonos, datos de pago)?

4. Abuso del login y hosting

Revisión 4, login y hosting.
1. Login, registro, recuperar contraseña y cualquier ingreso de códigos: ¿qué limita el número de intentos? Revisa la configuración de límites de autenticación y cualquier endpoint propio. Di qué impide que un bot adivine para siempre.
2. ¿Los buckets de almacenamiento son privados donde deben serlo? Lista cada bucket, si es público y sus políticas.
3. ¿La base de datos solo se alcanza a través de su API, sin una cadena de conexión directa abierta en algún lugar público?
4. ¿Los despliegues de prueba o staging usan claves y datos separados, o apuntan a producción?

5. Entradas a la IA (solo si tu app usa IA)

Revisión 5. ¿Alguna función envía texto escrito por usuarios, archivos subidos o contenido web a un modelo de IA? Si es así: ¿ese contenido se trata estrictamente como datos, nunca como instrucciones? ¿Puede hacer que la IA use una herramienta, revele un prompt de sistema o escriba en la base de datos? Si no se usa IA en ningún lado, dilo y salta esta revisión.

6. Respaldos, y luego el resumen

Revisión 6, preparación para producción. ¿Están activados los respaldos de la base de datos, y alguna vez se probó una restauración? ¿Desde dónde restauraríamos y cuánto tardaría? Luego resume las seis revisiones: primero los hallazgos BLOQUEANTES, cada uno con VERIFICADO o SUPUESTO, archivo:línea y una idea de corrección en una línea. No corrijas nada.

Después de la revisión

Corrige primero los hallazgos BLOQUEANTES, uno por uno, y vuelve a correr la revisión que encontró cada uno. Luego agrega reglas permanentes para que el agente no deshaga el trabajo la semana siguiente. Ponlas en el archivo de instrucciones de tu agente (CLAUDE.md en Claude Code, AGENTS.md en Codex):

## Reglas de seguridad
- Nunca desactives la seguridad a nivel de fila ni aflojes una política para arreglar un error. Detente y pregunta.
- Las claves secretas nunca llegan al navegador ni a una variable pública (VITE_ / NEXT_PUBLIC_).
- Ninguna función de servidor sin verificar identidad y rol del lado del servidor.
- Los endpoints de login e ingreso de códigos tienen límite de intentos.
- Detente y pregunta antes de cambiar algo público: buckets, políticas, configuración de autenticación.
