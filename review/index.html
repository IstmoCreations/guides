Set up an adversarial review for your AI builds

For people who build with Claude Code or another AI agent, not just chat. One AI leads and builds. A different AI, from a different company, attacks the plan before any code exists and the code after it's built. You rule on every finding.

Codex runs inside Claude Code through OpenAI's codex-plugin-cc (Apache-2.0). The "try to break into your own app" idea comes from Kem (@kem_glitch); our security check guide turns it into prompts. Not sponsored by anyone.

Why bother

The AI that wrote something is the worst judge of it: it grades its own homework. In my first two builds with this setup, every problem the review found was in the plan, not the code. A plan review is the cheapest place to catch a mistake, because nothing has been built on it yet.

What you need

  • Claude Code (the lead in most of my builds).
  • Codex, OpenAI's coding agent. The plugin needs a ChatGPT subscription (the Free plan counts) or an OpenAI API key, and Node.js 18.18 or later. Check its README for the current terms; reviews count toward your Codex usage limits.

Install, inside Claude Code:

/plugin marketplace add openai/codex-plugin-cc
/plugin install codex@openai-codex
/reload-plugins
/codex:setup

That gives you /codex:review (a normal read-only review) and /codex:adversarial-review (a challenge review you can steer). No plugin? The loop still works: paste the message below into a second AI by hand.

The loop

StepWho
1. Write the plan: what will change, in which files, and how you'll know it workedLEAD
2. Attack the planREVIEWER
3. Rule on every finding: fix it, or reject it with a reasonLEAD
4. Build it (nothing is built while a finding is still open)LEAD
5. Attack the result, with the diff in handREVIEWER
6. Rule on those findings, then the final callLEAD (and you sign off)

The seats swap. Either AI can lead. When one is running low on usage, swap: the other one leads and builds, and the first one reviews. Whoever leads makes the final call. The one rule that never changes: no AI reviews its own work.

The review message (steps 2 and 5)

An open "review this" lets the reviewer read your whole project and costs a lot. This shape, everything inline, three exact questions, cut my reviews to a fraction of the cost and made them sharper.

You are reviewing a plan written by a different AI. Your job is to find what will break, not to be agreeable.

Everything you need is in this message. Do NOT read the project. If something you need is missing, answer "NEED: <exact file or detail>" and stop.

Before you look at the plan, write two sentences: how YOU would approach this change.

THE GOAL: [one paragraph: what this change is for, and how we'll know it worked]

THE PLAN: [paste the plan]

THE CODE IT TOUCHES: [paste the relevant code, with file names and line numbers]

Answer only these three questions:
1. [the question that decides whether this works]
2. [the question about what could go wrong for a real user]
3. [the question about what the plan forgot]

For every claim, write VERIFIED (you can point to the line that proves it) or ASSUMED (you are inferring). Give each question a verdict: OK / AMEND / BLOCK. End with a list called "What this message did not show me".

For the code review (step 5), paste the diff and the tests instead of the plan, and ask whether the code does what the plan promised.

Ruling on findings (steps 3 and 6)

  • Every finding gets one answer: fixed, or rejected, because … Write the reason down.
  • A reviewer that you agree with every single time isn't reviewing; you're obeying. Reject what doesn't change the outcome.
  • Trust VERIFIED over ASSUMED. An ASSUMED finding is a question to check, not a fact.
  • If the findings grow every round instead of shrinking, stop: the plan isn't ready to be reviewed yet.

Make it a rule

Put this in your instructions file (CLAUDE.md for Claude Code, AGENTS.md for Codex) so the agent runs the loop without being asked:

## Adversarial review (every build beyond a one-line fix)
1. Write the plan first, with a goal and how we'll know it worked.
2. Send the plan to the other AI for review (Codex via /codex:adversarial-review, or by hand) using the review message: everything inline, three questions, VERIFIED vs ASSUMED.
3. Do not build while any finding is unaddressed. Each one is fixed, or rejected with a stated reason.
4. Build. Then send the diff and the tests back for a code review, and rule on those findings the same way.
5. No AI reviews its own work. Whoever leads makes the final call; I sign off.

Monta una revisión adversarial para lo que construyes con IA

Para quien construye con Claude Code u otro agente de IA, no solo chatea. Una IA lidera y construye. Otra IA, de otra empresa, ataca el plan antes de que exista código, y el código después. Tú decides cada hallazgo.

Codex funciona dentro de Claude Code con el plugin codex-plugin-cc de OpenAI (Apache-2.0). La idea de "intenta entrar a tu propia app" es de Kem (@kem_glitch); nuestra guía de revisión de seguridad la convierte en prompts. Sin patrocinio de nadie.

Por qué vale la pena

La IA que escribió algo es la peor jueza de su trabajo: se pone su propia nota. En mis dos primeros proyectos con este método, todos los problemas que encontró la revisión estaban en el plan, no en el código. Revisar el plan es lo más barato, porque todavía no se ha construido nada encima.

  • Claude Code (el líder en la mayoría de mis proyectos).
  • Codex, el agente de código de OpenAI. El plugin necesita una suscripción de ChatGPT (el plan gratis cuenta) o una clave de API de OpenAI, y Node.js 18.18 o más nuevo. Revisa su README para las condiciones actuales; las revisiones cuentan contra tus límites de uso de Codex.

El ciclo

PasoQuién
1. Escribir el plan: qué cambia, en qué archivos y cómo sabremos que funcionóLÍDER
2. Atacar el planREVISOR
3. Decidir cada hallazgo: arreglarlo, o rechazarlo con una razónLÍDER
4. Construirlo (nada se construye mientras haya un hallazgo abierto)LÍDER
5. Atacar el resultado, con los cambios en la manoREVISOR
6. Decidir esos hallazgos y dar la última palabraLÍDER (y tú apruebas)

Los puestos se intercambian. Cualquiera de las dos IA puede liderar. Cuando a una le queda poco uso, se cambian: la otra lidera y construye, y la primera revisa. Quien lidera tiene la última palabra. La única regla que nunca cambia: ninguna IA revisa su propio trabajo.

El mensaje de revisión (pasos 2 y 5)

Un "revisa esto" abierto deja que el revisor lea todo tu proyecto y cuesta mucho. Esta forma, todo dentro del mensaje y tres preguntas exactas, bajó mis revisiones a una fracción del costo y las hizo más precisas. Puedes pegarlo tal cual; la IA responde en español si se lo pides.

You are reviewing a plan written by a different AI. Your job is to find what will break, not to be agreeable.

Everything you need is in this message. Do NOT read the project. If something you need is missing, answer "NEED: <exact file or detail>" and stop.

THE GOAL: [one paragraph: what this change is for, and how we'll know it worked]

THE PLAN: [paste the plan]

THE CODE IT TOUCHES: [paste the relevant code, with file names and line numbers]

Answer only these three questions:
1. [the question that decides whether this works]
2. [the question about what could go wrong for a real user]
3. [the question about what the plan forgot]

For every claim, write VERIFIED (you can point to the line that proves it) or ASSUMED (you are inferring). Give each question a verdict: OK / AMEND / BLOCK. End with a list called "What this message did not show me".

Para la revisión del código (paso 5), pega los cambios (el diff) y las pruebas en lugar del plan, y pregunta si el código hace lo que el plan prometió.

Cómo decidir los hallazgos (pasos 3 y 6)

  • Cada hallazgo recibe una respuesta: arreglado, o rechazado, porque … Escribe la razón.
  • Si estás de acuerdo con el revisor todas las veces, no estás revisando: estás obedeciendo. Rechaza lo que no cambia el resultado.
  • Confía más en VERIFIED que en ASSUMED. Un hallazgo ASSUMED es una pregunta que comprobar, no un hecho.
  • Si los hallazgos crecen en cada ronda en vez de bajar, para: el plan todavía no está listo para revisarse.
